Phase 5 questions for Team 2. Each has a proposed answer; nothing is decided until Team 2 agrees. Record the outcome in `docs/decisions.md`. Answers that change `docs/openapi.yaml` go into one contract commit that both teams apply.

1. Which `ReportData` fields belong to each report stage, and which of them are required (listed in `missing_fields` when absent)? The Phase 2 grader took a point off Section 5.1 because the spec never said.
   - Proposed answer: follow CRA Art. 14(2). `early_warning`: `member_states` (required). `vulnerability_notification`: `product_information`, `exploit_nature`, `vulnerability_nature`, `corrective_measures_taken`, `user_mitigations` (required) and `sensitivity` (optional, "where applicable"). `final_report`: `vulnerability_description`, `severity`, `impact`, `corrective_measure_details` (required) and `malicious_actor_information` (optional, "where available"). This matches the Section 5.2 example, which returns `missing_fields: []` for a notification without `sensitivity`. Optional fields appear in `data` when supplied and never in `missing_fields`.
2. When is a required field "missing"?
   - Proposed answer: when it is absent, `null`, a string that is empty or only whitespace, or (for `member_states`) an empty array. Values are stored and returned exactly as sent; no trimming.
3. What does `PUT .../report-data/{stage}` do to data already stored for that stage, and what does its 200 response contain?
   - Proposed answer: it replaces the stage's whole data set (HTTP PUT semantics), so a field left out of the body is no longer stored. The 200 response body is the `GeneratedReport` for that stage, as `GET .../reports/{stage}` would return it at that moment (added to the contract; the contract currently gives the 200 no body).
4. What happens to a field that belongs to another stage, a field that isn't in `ReportData`, or a value of the wrong type?
   - Proposed answer: 400 `INVALID_REQUEST` naming the field (for example `severity does not belong to stage early_warning`), and nothing is stored. `member_states` must be an array of non-empty strings; every other field must be a string. Country codes are not validated.
5. What do the two report operations return for an invalid stage name, an unknown incident, a voluntary incident, and the final report before `fix_available_at` is recorded?
   - Proposed answer: invalid stage → 400 `INVALID_REQUEST` on both operations (added to the contract for `GET .../reports/{stage}`, which lists only 200 and 404 today); unknown incident → 404 `INCIDENT_NOT_FOUND`; voluntary incidents and a final report before the fix are allowed, because report data is independent of deadlines.
6. What goes in `data` and `generated_at`, and does generating a report change anything?
   - Proposed answer: `data` holds only the stage's supplied fields (no nulls, no fields from other stages, no system-filled fields); `generated_at` is the clock's current time (the test clock when set). Generating is a read: nothing is stored and nothing is audited.
7. What must the audit log show for AC-09: which actions are logged and under which names, what timestamp each entry carries, and how is "chronological" checked?
   - Proposed answer: every successful state change through the application interface writes exactly one entry; failed requests, reads and the test-control endpoints (`/api/v1/test/*`) write none. Agree one action vocabulary: `RELEASE_REGISTERED`, `SBOM_STORED`, `SBOM_REPLACED`, `INCIDENT_CREATED`, `FIX_AVAILABLE_RECORDED`, `SUBMISSION_RECORDED`, `REPORT_DATA_STORED`, with `entity_type` `release` or `incident` and `entity_id` the affected release or incident. `timestamp` is the clock's time when the change was made (the test clock when set), so the ±2 s check compares against the clock the tester set. Events come back oldest first; tests check the array order and that timestamps never decrease.
8. How is AC-10 (state survives a process restart) run across teams, given that a tester can't restart another team's server over HTTP?
   - Proposed answer: in two steps with no contract change. The tester seeds data and saves a snapshot; the system's owner restarts the service (or the evaluator does, with access) and tells the tester; the tester sets the same test clock again (it is in memory) and compares. Alternative, if Team 2 prefers full automation: a test-only `POST /api/v1/test/restart` (202) that exits the process so its supervisor restarts it, added to the contract.
9. Team 2's Phase 4 run found four timestamp and input cases. Do both teams behave the same way on them?
   - Proposed answer: a trailing newline makes a timestamp, date or CVE ID invalid (400); lowercase `t` and `z` are accepted and returned as `T` and `Z` (RFC 3339 §5.6); the SBOM upload accepts `application/json` and `application/vnd.cyclonedx+json` (parameters such as `charset` allowed) and returns 400 `Content-Type must be application/json` for anything else, including a missing header; body text that isn't UTF-8 returns 400 with a message that says the body is not valid JSON.
10. When do the final cross-team runs happen, and how do we avoid wiping each other's data mid-run?
   - Proposed answer: each team posts in the pod chat before a run against the other's URL, runs both directions in one agreed window before the Phase 5 deadline, and records each run in its own repo. The target owner re-seeds demo data afterwards.
11. (Carried from Phase 4, Q7.) Who on each team verifies the AC-04 fixtures, and the new AC-08 fixtures in `fixtures/report_cases.json`, and by when? Team 6 has checked the AC-04 fixtures (Donovan Baran, 2026-11-18; evidence in `fixtures/README.md`) and needs Team 2's checker for the same values.
   - Proposed answer: one named person per team for each fixture set, before the final cross-team runs.
