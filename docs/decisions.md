# Decisions

Agreed answers and outstanding proposals are recorded below. Proposed details still need pod (Team 2) confirmation. Team 2's answers to the Phase 4 questions (`docs/pod-questions-phase4.md`) arrived on 2026-11-01.

| Topic | Answer | Status |
|---|---|---|
| Missing `X-User-Id` | Endpoints requiring the header return 400 with `INVALID_REQUEST` when it is missing. Test-control endpoints are exempt. | agreed |
| CycloneDX versions | Accept valid CycloneDX JSON with `specVersion` 1.4, 1.5, or 1.6. Reject unsupported versions with 400 and an explanatory message. | agreed |
| Component without `version` | Reject the entire SBOM with 400 if an inventory component, including a nested component, is missing a required version. | agreed |
| Error-code assertions | Check exact error codes for explicitly agreed cases, alongside HTTP statuses and meaningful nonempty messages. For other cases, check the status and error envelope until specific code values are agreed. | recommended |
| Nested components | Recursively flatten nested inventory components and include every component at every depth in storage and `component_count`. Proposed details: exclude metadata and tool components, and retain repeated occurrences unless agreed otherwise. Implementation: document order, each parent before its children; a missing version at any depth rejects the SBOM with the component's path. | recursive flattening agreed; exclusions and repeated occurrences proposed |
| Unregistered release + SBOM | Check release existence before validating the SBOM body. Unknown release IDs return 404. | agreed |
| SBOM schema strictness | Official CycloneDX schemas bundled with `cyclonedx-python-lib` (non-vendored); unknown properties that the official schema forbids are rejected | implementation choice |
| Shared fixtures | `fixtures/` (25-component SBOM and releases fixture) reviewed by Team 6 and used unchanged by both teams | agreed with Team 2 (2026-10-17) |
| Timestamp format (§10 Q1) | Inputs may end in `Z` or a numeric offset (`+02:00`, `-00:00`, up to ±23:59) and are converted to UTC; a timestamp with no zone is 400. Fractional seconds are kept (truncated beyond microseconds). Outputs always end in `Z`: whole seconds without a fraction, otherwise six digits (`2026-11-01T23:59:59.100000Z`). One parser and formatter in `app/clock.py`. | agreed with Team 2 (2026-11-01) |
| Deadline statuses (Q2) | A stage submitted at or before its deadline is `met`. Unsubmitted, it is `pending` while now ≤ deadline and `overdue` from one second later. A late submission stays `overdue` with `submitted_at` set (no `late` status). Voluntary cases, and the final report before `fix_available_at`, are `not_applicable` with `deadline_at: null`. | agreed with Team 2 (2026-11-01) |
| Submission errors (Q2) | A second submission for the same stage is 409 `SUBMISSION_EXISTS` (added to the contract); a submission for a `not_applicable` stage is 400. | agreed with Team 2 (2026-11-01); contract addition in c249e2c, which Team 2 applies to their copy |
| Incident timestamps (Q3) | `submitted_at` or `fix_available_at` earlier than `awareness_at` is 400. Times later than the clock's now are accepted. A second `fix_available_at` overwrites the first and is audited again. On a voluntary incident it is stored, but every deadline stays `not_applicable`. | agreed with Team 2 (2026-11-01) |
| Malformed CVE ID; incident `cve_id` (Q4) | A CVE ID that doesn't match `^CVE-[0-9]{4}-[0-9]+$` is 400 `INVALID_REQUEST` on the CVE query (added to the contract) and on incident creation. An incident's `cve_id` needs only that format; it needn't be known to the source. | agreed with Team 2 (2026-11-01); contract addition in c249e2c, which Team 2 applies to their copy |
| Purl matching (Q5) | A component matches when its purl equals an affected purl after both have their qualifiers (`?…`) and subpath (`#…`) removed. `affected_purls` list exact versions only. A component without a purl never matches. | agreed with Team 2 (2026-11-01) |
| Vulnerability source after reset (Q6) | `POST /test/reset` leaves the source `available` with zero records, so every CVE is unknown. `PUT /test/vulnerability-source` replaces all records (and the mode). | agreed with Team 2 (2026-11-01) |
| AC-04 fixtures and ordering (Q7) | One person per team checks the expected values before the Phase 4 milestone. Cross-team tests compare affected releases and matched components as sets, not by order. Until both teams' checkers sign off, `fixtures/ground_truth.json` is a draft and AC-04 is not authoritative. | agreed with Team 2 (2026-11-01): one reviewer per team verifies the values before the Phase 4 submission. **Team 6 checker: Donovan Baran, 2026-11-18**: every `affected_purls` range confirmed against the GHSA and PYSEC advisories (OSV), the grouping at `2026-11-01T23:59:59Z` and the recomputed `ground_truth.json` match, no value changed (evidence: `fixtures/README.md`). Team 2's checker not yet named (P5-Q11), so the fixtures stay drafts |
| Production vulnerability source; alerts (Q8) | Proposed: switch from Dependency-Track to a local OSV snapshot (needs instructor sign-off, so not built yet; every graded test uses the fixture source, `VULN_SOURCE=fixture`). No push alerts in Phase 4: deadline status is shown on every read. | no push alerts: agreed with Team 2 (2026-11-01). OSV snapshot instead of Dependency-Track: Team 2 open to it (2026-11-01); instructor sign-off pending, not built |

## Phase 5

Questions and proposed answers: `docs/pod-questions-phase5.md` (P5-Q1..Q11). Team 2 received a shorter version with eight questions (their Q1 = P5-Q1, Q2 = P5-Q2, Q3 = P5-Q3 and Q6, Q4 = P5-Q4 and Q5, Q5 = P5-Q7, Q6 = P5-Q8, Q7 = P5-Q9, Q8 = P5-Q10 and Q11).

**Team 2's answers (recorded 2026-11-22):** Team 2 agreed to all eight. They added three clarifications, all of which match what we built: `null` counts as missing (accepted and listed in `missing_fields`), not as a wrong type; audit events with the same timestamp keep the order they were recorded in; and tests of the invalid-UTF-8 case should check the 400 status and a non-empty message, not the exact text, because Team 2's wording differs. They will apply contract commit `0b3432d` (the PUT 200 body and the GET 400 for an invalid stage) to their copy. Their Q8 reply still left the AC-04 and AC-08 checkers, their final URLs and the run window blank, so P5-Q10 and P5-Q11 stay open.

**Built before the answers (2026-11-18, Daksh Agarwal):** the report endpoints, AC-08, AC-09 and AC-10 were built on the proposed answers, and the checks that rested on them were made informational in the tester (CLAUDE.md §7 rule 4). Those checks are still informational; now that Team 2 has agreed, they can be made required.

| Topic | Answer | Status |
|---|---|---|
| Trailing whitespace (P5-Q9) | A timestamp, date or CVE ID with a trailing `\n`, `\r\n` or space is 400 `INVALID_REQUEST`, and nothing is stored. Every Python validation regex uses `fullmatch`. | agreed by Team 2; built in `ce44401` |
| Lowercase `t` and `z` (P5-Q9) | Accepted in every timestamp (RFC 3339 §5.6), e.g. `2026-11-01t23:59:59z`; output is always `…T…Z`. A timestamp with no zone is still 400. Amends the Phase 4 timestamp-format answer above. | agreed by Team 2; built in `50928bd` |
| SBOM media type (P5-Q9) | The SBOM upload accepts `application/json` and `application/vnd.cyclonedx+json` (parameters such as `charset` allowed, case-insensitive); anything else is 400 `INVALID_REQUEST` `Content-Type must be application/json`, checked after the 404 for an unknown release. Our Phase 4 report proposed 415; the pod chose 400, which the contract lists. | agreed by Team 2; built in `416c069` |
| SBOM with no `Content-Type` (P5-Q9) | 400 `INVALID_REQUEST`, like any other non-JSON type. | agreed by Team 2; **not built yet**: still accepted (`ALLOW_MISSING_CONTENT_TYPE = True` in `app/routers/sbom.py`); flip it and deploy before the final cross-team run |
| Invalid-UTF-8 SBOM body (P5-Q9) | 400 `INVALID_JSON` with the message `request body is not valid JSON: not UTF-8 text`. Tests check the status and a non-empty message, not the wording. | agreed by Team 2; built in `43d3e33` |
| Report fields per stage (P5-Q1) | CRA Art. 14(2). `early_warning`: `member_states` (required). `vulnerability_notification`: `product_information`, `exploit_nature`, `vulnerability_nature`, `corrective_measures_taken`, `user_mitigations` (required), `sensitivity` (optional). `final_report`: `vulnerability_description`, `severity`, `impact`, `corrective_measure_details` (required), `malicious_actor_information` (optional). | agreed by Team 2; built |
| What counts as missing (P5-Q2) | A required field that is absent, `null`, an empty or whitespace-only string, or an empty `member_states` array. `null` is accepted and listed as missing, not rejected as a wrong type. Values are stored and returned exactly as sent. | agreed by Team 2; built |
| Report-data PUT (P5-Q3) | Replaces the stage's whole data set; the 200 body is the stage's `GeneratedReport` (contract addition). | agreed by Team 2; built; Team 2 applies `0b3432d` to their copy |
| Report-data validation (P5-Q4) | Another stage's field, an unknown field, or a wrong type is 400 `INVALID_REQUEST` naming the field; nothing is stored. `member_states` is an array of non-empty strings; every other field a string. Country codes aren't validated. | agreed by Team 2; built. The version Team 2 received said only "wrong type", not "non-empty strings": confirm they also reject `["", "DE"]` |
| Report stages (P5-Q5) | Invalid stage → 400 `INVALID_REQUEST` on both operations (contract addition for the GET); unknown incident → 404 `INCIDENT_NOT_FOUND`, checked first; voluntary incidents and a final report before the fix are allowed. | agreed by Team 2; built; Team 2 adds the GET 400 to their copy |
| Generated report (P5-Q6) | `data` holds only the stage's supplied fields (no nulls, no other stages, nothing system-filled); `generated_at` is the clock's now. Generating stores and audits nothing. | agreed by Team 2; built |
| Audit log (P5-Q7) | One entry per successful state change; none for failed requests, reads or `/api/v1/test/*`. Actions `RELEASE_REGISTERED`, `SBOM_STORED`, `SBOM_REPLACED`, `INCIDENT_CREATED`, `FIX_AVAILABLE_RECORDED`, `SUBMISSION_RECORDED`, `REPORT_DATA_STORED`; `entity_type` `release` or `incident`. `timestamp` is the clock's time; events oldest first, and events with the same timestamp in the order they were recorded. | agreed by Team 2; built |
| Stale CPEs in `sbom_patched.json` (AC-04) | The `syft:cpe23` properties on werkzeug 2.2.3 and flask 2.2.5 still name 2.2.2. Left unchanged: matching uses purls only (Q5), so no expected result depends on them. | Team 6 decision (Donovan Baran, 2026-11-18); tell Team 2 with the P5-Q11 request |
| AC-10 across teams (P5-Q8) | Two steps, no contract change: the tester seeds and snapshots; the owner restarts the service; the tester sets the same clock and compares. | agreed by Team 2; built |
| Final cross-team runs (P5-Q10) | One agreed window, both directions, announced in the pod chat; the target's owner re-seeds afterwards. | agreed by Team 2; **open:** Team 2's final URLs and the window |
| Fixture checkers (P5-Q11) | One checker per team for the AC-04 and AC-08 fixtures. Team 6's AC-04 check is done (Donovan Baran, 2026-11-18). | agreed by Team 2; **open:** Team 2's two checkers, and Team 6's AC-08 checker |
